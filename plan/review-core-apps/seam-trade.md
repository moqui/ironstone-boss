# Seam review: trade flows (procure to pay, order to cash, returns, cases and portals)

Phase 2, Oct 28, 2026. Read-only review; no repository files were edited.

**Abbreviations.** Design files are in `runtime/component/mr-boss/plan/`: XC = design-crosscut.md, PUR = design-purchasing.md,
WH = design-warehouse.md, AC = design-accounting.md, CS = design-customer-service.md, PRD = design-products.md,
PRJ = design-projects.md, DC = design-drawers-commons.md. `M:` = `runtime/component/mr-mantle/` (active XML only; comments
ignored). `B:` = `runtime/component/mr-boss/`. References are `file:line`. "Code-read" means I verified the behavior by
reading active XML; nothing was executed.

**Mantle behavior this review relies on (all code-read).**

1. Incoming ShipDelivered runs `create#PurchaseShipmentInvoices` (M:service/AccountingInvoice.secas.xml:26-35). That
   service bills each ShipmentItemSource quantity. It writes accepted AssetReceipt lines first
   (M:service/mantle/account/InvoiceServices.xml:1142, 1187, 1256-1290). Whatever remains becomes a line without an asset
   (:1306-1312). `deliver#Shipment` lowers the source quantity only to accepted plus rejected
   (M:service/mantle/shipment/ShipmentServices.xml:2125-2137, 2281-2300; `update#ShipmentItem` :133-283). The result is that
   dock-rejected units are billed at the PO price, and so are units accepted into quarantine.
2. Outgoing ShipPacked runs `create#SalesShipmentInvoices` (AccountingInvoice.secas.xml:16-25). `pack#Shipment` first lowers
   the sources to the handled quantity (ShipmentServices.xml:2080), so a short pack is not overbilled. The invoice
   then applies and captures the order payments (InvoiceServices.xml:1511-1522; M:service/mantle/account/PaymentServices.xml:924, 957).
   `complete#ShipmentPack` runs `pack#Shipment` in its own transaction (`force-new`) and gates labels on payment
   coverage of the invoice (ShipmentServices.xml:1959-1990). Once a source has an invoice, `unpack#ShipmentItemIssuance`
   refuses it (:1579).
3. Return shipment sources carry `returnId`, not `orderId` (M:service/mantle/order/ReturnServices.xml:1254-1257). Both
   invoice SECAs skip sources without an `orderId` (InvoiceServices.xml:1117). Return shipments therefore create no invoice.
4. ReturnApproved runs `create#ReturnShipment` and `process#ReturnItemResponses` (M:service/OrderReturn.secas.xml:69-77).
   At approval, that service processes every `responseImmediate=Y` item and every RrspReplace item
   (ReturnServices.xml:710-713). ShipDelivered on a ShpTpSalesReturn runs `receive#ReturnShipmentItems`
   (OrderReturn.secas.xml:80-83). That service counts only `quantityAccepted` (ReturnServices.xml:545-557), and ReturnReceived
   processes the responses again (OrderReturn.secas.xml:87-90). On a partial receipt with no response yet,
   `receive#ReturnItem` cuts `returnQuantity` down to the received quantity and closes the item (ReturnServices.xml:619-622).
   `process#ReturnItemResponses` does nothing for supplier returns (:690). No service sets ReturnShipped.
5. Returnable quantity is the invoiced quantity minus the returned quantity, from OrderItemBilling
   (ReturnServices.xml:270-349). This holds for both directions.
6. Order status transitions: OrderBeingChanged can be entered only from OrderOpen or OrderProposed
   (M:entity/OrderEntities.xml:183-199). Placed, Processing and Approved can go to Hold, and Hold can go to
   Approved/Placed/Processing/Cancelled (:189-223). There is no Sent→Hold transition. Mantle treats Placed and Hold as
   editable (M:service/mantle/order/OrderInfoServices.xml:175).
7. On OrderPlaced, SECAs reserve stock (M:service/ProductAsset.secas.xml:25-27), authorize payments
   (M:service/AccountingPayment.secas.xml:17-19), send the placed email and call `autoApprove#Order`
   (OrderReturn.secas.xml:17-44). `autoApprove#Order` approves when Authorized/Delivered/Confirmed payments on the order
   cover `grandTotal` and `check#OrderPreApprove` returns no warnings. That check is documented as the SECA extension
   point (M:service/mantle/order/OrderServices.xml:1226-1268; OrderInfoServices.xml:834-836). Manual `approve#Order` checks
   only ORDER_APPROVE (OrderServices.xml:1181-1192). A shipment can be created only for an Approved or Sent part
   (ShipmentServices.xml:519-539).
8. `send#OrderStoreEmail` and `send#InvoiceStoreEmail` return without sending when there is no ProductStore
   (OrderInfoServices.xml:1368 ff.; InvoiceServices.xml:2806, 2825). InvoiceFinalized automatically sends
   store invoices (AccountingInvoice.secas.xml:78-83).
9. Payments with `forInvoiceId` are applied automatically on payment delivery and on invoice approval
   (AccountingPayment.secas.xml:33-35; AccountingInvoice.secas.xml:60-64). Nothing in Mantle knows about an invoice hold.
10. Existing external-access conventions:
    - Token routes (`/s`, `/u`, `/cal`, `/r`) are configured with a token-service check and a per-route rate limit
      (B:MoquiConf.xml:13-24) and use `require-authentication="false"` screens at the screen root
      (B:screen/RequestIntake.xml, PublicShare.xml).
    - Authenticated client users get an internal app root under a user group with entity filter sets, with internal
      screens and writes denied (BOSS_PROJECT_CLIENT; B:screen/Projects.xml:15-31; B:service/ironstone/client/ClientServices.xml).
    - `mantle.public.PublicAccessGrant` is keyed by party and site; `siteId` already exists. It is a PASS grant, not a
      bearer token (M:entity/PublicEntities.xml:98-112).
11. The built shared OrderDetail and InvoiceDetail call only `ironstone.projects.BillingServices`
    (B:screen/Shared/OrderDetail.xml:33, 42; InvoiceDetail.xml:42-88). The built RequestDetail has no create-PO transition;
    its Items tab is a read-only list (RequestDetail.xml:812-836).
